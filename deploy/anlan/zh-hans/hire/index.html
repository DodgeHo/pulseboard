我的工程方法

我关注第一次成功请求之后仍然重要的决策。

我把后端行为、运维和用户界面视为同一个工程问题。API 不会在 happy path 成功后就算完成；访问边界、持久化选择、异步工作、健康信号、恢复程序与文档，共同决定系统能否被维护。

可靠性工作必须具体才有价值。我偏好可执行、可评审、可重复的检查与演练：分离 liveness 与 readiness、worker recovery、备份恢复、rollback 程序及明确契约。

我也重视最后一公里。稳健的系统应提供实用界面与清晰评审路径，而不是用视觉包装或夸大的陈述掩盖不确定性。

公开边界

这些说明让证据保持准确，并降低评审时的不确定性。

  1. 作品集语境

    PulseBoard 是 production-shaped portfolio project，不是真实服务商业客户的生产系统。

  2. 通知交付

    通知 provider 是 mock-compatible。项目不声称已接入真实第三方生产通知服务。

  3. 云端范围

    AWS 资源尚未创建。云端架构材料是设计证据，不是运行中 AWS 基础设施的证明。

  4. 恢复证据

    备份恢复与 rollback 属于本地或 CI 演练，不能证明大规模生产环境的 RPO/RTO 表现。
